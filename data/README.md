# P24 — Data dictionary + known quirks

## The source files — `data/raw/` (SAMPLE)

SAMPLE files for the fictional wholesale distributor **Khan Traders,
Lahore**, Thu 2026-01-01 → Tue 2026-06-30 (6 months, 181 days).
Generated by `src/generate_data.py` (seed 20261120). 600 sale lines,
180 purchase lines, 40 products, 25 customer shops, 8 suppliers.

### `sales_SAMPLE.csv` — 600 lines (592 clean + 8 planted defects)

| Column | Type | Meaning |
|---|---|---|
| order_id | text | `ORD-0001` …; an order can have several lines |
| sale_date | text | `yyyy-mm-dd`; the sale day |
| customer_id | text | `CUS-01` … `CUS-25`; the shop that bought |
| product_code | text | `PRD-001` … `PRD-040`; must exist in the product master |
| qty | integer | Units sold on this line (must be > 0) |
| unit_price_pkr | integer | Sell price per unit in PKR (from the product master) |
| line_total_pkr | integer | Must equal `qty × unit_price_pkr` |

**Planted defects (8 lines, found exactly by the DQ tests):**

| Defect | Lines | Detail |
|---|---|---|
| Exact duplicate lines | 2 | Raw lines 30 & 391 are the same line (ORD-0095, PRD-035, qty 12, PKR 58,800); raw lines 441 & 598 are the same line (ORD-0206, PRD-003, qty 8, PKR 34,400). Staging keeps the first occurrence. |
| qty ≤ 0 | 3 | Raw line 37 (ORD-0243, PRD-039, qty −1, PKR −1,300); line 48 (ORD-0244, PRD-021, qty −2, PKR −11,800); line 338 (ORD-0242, PRD-016, qty 0, PKR 0). |
| Unknown product | 2 | Raw line 215 (ORD-0246, product PRD-888); line 297 (ORD-0245, product PRD-999). Neither code exists in the product master. |
| Wrong line total | 1 | Raw line 175 (ORD-0247, PRD-023, qty 3 × PKR 6,350 = PKR 19,050, but recorded as PKR 19,550 — PKR 500 too high). |

The raw gross of all 600 lines is PKR 27,321,100. The clean gross of
the 592 staged lines is PKR 27,211,450 — the PKR 109,650 difference is
exactly the 8 rejected lines (PKR 58,800 + 34,400 duplicates,
PKR −1,300 − 11,800 + 0 bad quantities, PKR 10,000 unknown products,
PKR 19,550 wrong total).

| Column | Type | Meaning |
|---|---|---|
| po_id | text | `PO-0001` …; one line per purchase order in this sample |
| purchase_date | text | `yyyy-mm-dd`; the purchase day |
| supplier_id | text | `SUP-01` … `SUP-08`; who supplied it |

115–145% of sold qty per product), so no product ever goes negative
in stock.

## Reference lists (not CSVs — loaded from `sql/load_dimensions.sql`)

The customer and supplier masters are small reference lists the client
keeps outside the transaction exports, so they live as VALUES in the
dimension loader, not as CSVs:

- **dim_customer** — the 25 shops Khan Traders supplies (CUS-01 …
  CUS-25, name + area in Lahore).
- **dim_supplier** — the 8 suppliers (SUP-01 … SUP-08, name + city).

## Known quirks (read before quoting a number)

- **The 8.60% margin is a wholesale margin, not a retail one.** Khan
  Traders is a distributor: thin margins on high volume. Gross profit
  uses the product master's standard cost price, not the per-PO unit
  cost (which moves ±3% around it) — so profit is the margin on the
  price list, not on each individual purchase.
- **January looks like the best month (PKR 5,881,460) and February the
  weakest (PKR 3,159,800).** That is the sample's own seasonality
  (January restocking after the winter holidays, February short month),
  not a finding about the real market.
- **Every purchase order has exactly one line in this sample.** So
  `po_count` and `po_lines` are the same number (180) — on a real
  client file with multi-line POs they will differ, and the mart is
  written to count them separately.
- **dim_product is SCD Type 1.** A price change overwrites the old
  price; no price history is kept. If the client later needs history,
  the dimension becomes Type 2 (`valid_from` / `valid_to`) — the
  loader is the only file that changes.
